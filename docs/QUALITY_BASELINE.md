# Verification baseline before exporter changes

This batch adds verification tools only. Production capture, clipboard, popup and Figma importer code are unchanged from `43b4a73068d6f8c30040baeb99433b01c5f31220` (extension 1.6.0). A passing structural browser check is **not** a passing Figma acceptance check.

## Reproduce the browser measurements

```sh
npm run quality:serve
```

Open the printed localhost URL in Chromium. Set the viewport to 1440 × 1000 CSS pixels, leave the tab visible, close DevTools while measuring, and select **Run browser benchmark**. Download the report. Repeat at 768 × 1000; do not resize during a run. The suite has one discarded warm-up and three measured samples for each of five scenarios:

| Scenario | Purpose |
| --- | --- |
| Visual acceptance | Nested stacks, single paragraphs, rich text, SVG/CSS gradients, PNG/WebP and form geometry |
| 12 cards | Small repeated layout |
| 60 cards | Medium repeated layout |
| 150 cards | Larger tree below the capture limit |
| Long paragraphs | Text measurement and shaping pressure |

The benchmark imports the actual DOM capture, image normalization, native encoder and decoder. It does not mock Chrome APIs, install the extension, write the clipboard, upload evidence or touch a Figma document. A separate **Copy fixture for Figma acceptance** button explicitly writes the generated native HTML clipboard payload on click and exposes the same payload for isolated browser automation. It does not mark Figma checks passed or exercise installed-extension storage. Image normalization uses tiny local data URLs; it does not benchmark CDN downloads or the Chrome asset broker.

Reports include browser/version, viewport/DPR, CPU concurrency, source revision, extension version, per-stage timings, sample-level layer counts, serialized payload sizes, maximum observed frame gap and Long Task durations where supported. `totalMs` includes verification decoding; `captureMs + assetsMs + encodeMs` is the measured preparation path. Scheduling before/after a stage and real clipboard writes are excluded. Heap samples are optional Chromium JS heap readings at boundaries and on a timer, **not peak process memory**; synchronous work can hide a transient peak. These are warm runs, not extension cold-start measurements.

The source measurements and screenshots in `quality-baseline/` are source HTML evidence. No image in that directory should be described as Figma output.

### Recorded on 2026-10-21

Five structural scenarios passed at each of 1440 × 1000 and 768 × 1000 CSS pixels (three measured samples per scenario). The deeply nested purple/bold style observation was **false**: the existing capture consolidation loses that style. This is deliberately recorded as an outstanding fidelity issue, not fixed or counted as a successful fidelity check.

| Scenario | Desktop median capture / encode | Narrow median capture / encode |
| --- | --- | --- |
| Visual acceptance | 2 / 21 ms | 3 / 26 ms |
| 12 cards | 8 / 45 ms | 6 / 38 ms |
| 60 cards | 17 / 103 ms | 19 / 101 ms |
| 150 cards | 33 / 223 ms | 34 / 224 ms |
| Long paragraphs | 30 / 199 ms | 30 / 199 ms |

The 150-card fixture produced a maximum recorded Long Task of 245 ms at desktop width; this points to synchronous encoding as a performance target. These local warm-cache measurements do not establish real-site or low-powered-device speed. Layer counts were stable between repeated samples at each width. Counts differ between widths because the measured grid requires different native layout wrappers; compare each width to its own baseline.

## Regression comparison

```sh
npm run quality:compare -- docs/quality-baseline/browser-1440.json /path/to/new-browser-1440.json
```

Compare on the same machine, browser version, DPR, viewport and repetition count with similar background load. The comparator rejects mismatched recorded environments and missing/failed scenarios. It flags layer-count changes, previously passing structural/fidelity observations becoming false or missing, and median timing/payload increases exceeding both 25% and 50 ms (1 KiB for payloads). These are initial **review thresholds**, not product speed guarantees. An intentional change to layer structure requires inspecting and approving a replacement baseline. Source changes are expected between baseline and candidate; record the tested revision rather than relabelling a result.

CI runs metric-comparison unit tests and compiles the lab. It does **not** launch Chromium or Figma. Browser reports must be generated by running the page; Figma acceptance must be completed separately below.

## Actual extension → clipboard → Figma acceptance

Use a disposable Figma design file. Load/reload the built extension in Chrome, refresh the source fixture and wait for its ready message. Choose the white `#fixture` element using the installed extension. Use the normal **Copy to Figma** path, then focus the Figma canvas and paste. Do not use JSON import, a synthetic clipboard writer, or the decoded report as a substitute.

Before each capture, download **source measurements** and take a source screenshot. Record source revision, extension version, Chrome version, Figma desktop/web version, OS, CSS viewport, DPR, capture mode, warnings and timestamp. Save a Figma screenshot/export plus the results table. Repeat at desktop and narrow widths with fresh captures; a previously pasted snapshot is not expected to acquire new browser breakpoints.

## Rollback and scope

No runtime feature flag or rollout is needed for this batch: these files run only through the lab commands and verification CI. The shipped extension bundles and manifests keep their existing behavior/version. Preserve the baseline reports when subsequent changes are made. Test a small change against them and the Figma checklist before expanding scope.
